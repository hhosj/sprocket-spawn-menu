# SpawnMenu 开发笔记（维护者用，不面向玩家）

当前版本：0.5.4（准星落点 + 蓝图可视化 + 安全清场）。按用户确认：F10 真的生成；蓝图先扫描全表，
用 F8/F6 选、F10 生成（没有 UI）。
工作交接：`/home/hhosj/工作交接.md`（第 3 节是模组②的全部调研）。

## 本轮新确认的事实（补充交接文档）

### 1. 每帧挂钩点：优先 `GameController.SceneUpdate`，不是 `ModeUpdate`

交接文档 3.12 建议挂 `ScenarioGameMode` / `DeathmatchGameMode` / `DevelopmentGameMode` 的
`ModeUpdate`。实测 IL 后修正如下：

* `GameMode.ModeUpdate` 是 `protected virtual`，三个子类各有 override（dump.cs:902296 / 909590 / 909802），
  只挂基类确实不生效——这点交接文档是对的。
* 但 `GameMode.GameModeUpdate(GameTime)`（dump.cs:930371）是**public 非虚的公共入口**，
  函数体只有三条指令：取 vtable → 尾跳 `ModeUpdate`。
* `GameController.SceneUpdate`（Slot 7）里直接
  `mov rcx,[rbx+68h]`（gamemode）→ `mov rdx,[rbx+78h]`（gameTime）→ vtable 调用 `[rax+1A8h]`。
  即每帧调用的就是 `GameMode.GameModeUpdate`。

结论：**挂 `GameController.SceneUpdate` 一个点就够**（每帧、仅战斗场景、方法体大、好 patch）。
本项目另外把 `GameMode.GameModeUpdate` 也挂上作为兜底，用 `Time.frameCount` 去重。

### 2. 生成器可以脱离场景

* `IVehicleFactory.Factory` 是**接口上的静态字段**（dump.cs:722714），`IVehicleFactory` 提供
  `Create(blueprint, tech, flags, ct)`。
* `VehicleSpawner.ExecuteVehicleBuildAsync` 内部引用 `VehicleAssemblyResources` + `GetFactories()`
  （ISIL 里 `Call VehicleAssemblyResources.GetFactories`），说明工厂/组装阶段都从
  `assemblyResourcesOverride ?? VehicleAssemblyResources.Default` 来，不依赖场景里的某个组件。

所以“场景没有 `VehicleSpawner` 就自己 `new GameObject().AddComponent<VehicleSpawner>()`”是可行的
（本次探针就按这个实现，并在创建时把 `assemblyResourcesOverride` 指向 `Default`）。

### 3. 判断“有没有 AI”的可用信号

* `IVehicleEditGateway.BehaviourEnabled`（dump.cs:722968 附近）：车辆行为是否启用。
* `IVehicleRegister.Behaviours` 里的元素实现 `IAIControllableVehicle`，其 `ID` 是 `EntityID`，
  `EntityID.TeamID` 在 +0x3（dump.cs:950996）。**这是唯一能读到“载具实际队伍”的地方**
  （`IVehicleEditGateway` 本身没有 TeamID）。
* `VehicleAIAssemblyStageDefinition.GetAssemblyStage` 的条件（ISIL 实测）：
  `context.Target` 必须是 `IVehicleGateway`，且能拿到 `IVehicleBehaviour`，然后才
  `new VehicleAIAssemblyStage(...)`。也就是说**只要行为被启用，AI 阶段就会挂上**。

待实测：`VehicleSpawner.Spawn` 是否替我们调了 `EnableBehaviour`。探针会在生成完成后打印
`Vehicle.BehaviourEnabled` 和 register 里每个 behaviour 的 team。

### 4. 队伍/玩家队伍的可达路径

* `DeathmatchGameMode.playerTeamID`（private，0x58）。
* `ScenarioGameMode.sharedState`（`GameModeSharedState`，0x58）里有
  `VehicleRegister`、`PlayerVehicle`（`IVehicleEditGateway`）、`Player`。
* 探针会反射这两条路径；如果沙盒用的是别的模式，日志里会显示实际 GameMode 子类名。

### 5. 蓝图 API 与目录

`BlueprintLibrary` 把四个目录的蓝图合并、排序、去重；F9 时整表打印编号，F8/F6 移动光标，
F10 生成光标所指。`VehicleBlueprintFiler.GetVehicleBlueprintDirectory(GameDataDirectory)` +
`GetAllVehicleBlueprints(path)` + `VehicleBlueprintSerializer.LoadFromPath(path)` 均可用。
`GameDataDirectory`：`CurrentFaction=0`、`StreamingAssets=1`、`Documents=2`、`Factions=3`、
`Starter=4`、`PersistantData=5`。
`LastSavedVehicleBlueprint.TryGet(out string)` 仍是拿“玩家当前设计”的最短路径。

## 0.5.4：匹配不上就清空 AIRegister

0.5.3 日志里 `[cleanup]` 没有 `removed N AI(s)`，说明 `IsChildOf`/root 指针匹配失败；
AI 留在静态 `AIRegister`，`SetActive(false)` 清掉 avoidance 实体后，`Spherecast` 用旧 casterID
每帧 NRE。

0.5.4：匹配失败 → `AIRegister.Clear()`，并把 `AvoidanceEntityRegister.nextID` 范围内所有槽位
`Deregister`。清空后新一局重新注册；这次切换里所有 AI（含靶车）都会停。

## 0.5.3：手工摘 AI，别在编辑器里 Dispose

0.5.2 日志：`[cleanup] done (AIs 1 -> 0)` 证明 Dispose 清了 AI，但紧接着 `ExitEditor` 抛：

```
VehicleRegister.Register -> NullReferenceException
Vehicle.EnableBehaviour -> InvalidOperationException: Already enabled.
```

原因是我们在编辑器状态里 `Dispose` 了生成的载具，VehicleRegister 里留下脏项，玩家设计重建时
`EnableBehaviour` 失败，于是新坦克不能操控。

0.5.3 按 `VehicleAIAssemblyStage.Release()` 的顺序手工清理，不碰 factory：

1. `AvoidanceEntityRegister.Deregister(driver.avoidanceID)`
2. `AIRegister.Deregister(commanderAI)`
3. `CommanderAI.Release()`（取消任务/释放 driver）
4. `VehicleRegister.Deregister(vehicle)`
5. `gameObject.SetActive(false)`

AI 的匹配靠 `CommanderAI.observerTransform.root` / `controlTarget.transform.root` 与车辆根指针比较。

## 0.5.2：清场必须走游戏 Dispose，否则静态 AIRegister 留脏

0.5.1 日志（7MB）里，`[cleanup] match exit` 之后立刻开始刷：

```
NullReferenceException
  at AvoidanceEntityRegister.Spherecast(int casterID, Vector3 origin, float radius)
  at DriverAI.CollisionAvoidance(...)
  at DriverAI.Step(...)
  at CommanderAI.FastTick(...)
  at AIRegister.Update()
  at DeathmatchGameMode.ModeUpdate(...)
```

`AIRegister` 和 `AvoidanceEntityRegister` 都是 **static class**。0.5.1 只 `Deregister` + `SetActive(false)`，
AI 实体还在静态列表里，scene 卸载后继续 tick 已销毁对象；每帧异常导致新一局载具更新/操控全废。

正确清理：`VehicleSpawn.Dispose()` → `factory.Destroy()` → 车辆释放时
`VehicleAIAssemblyStage.Release()`（ISIL 里能看到它对 `AIRegister` 做 `List.Remove` 并
`CommanderAI.Release`）。0.5.0 在 `Dispose` 前先手动 `Deregister`，可能让这条路径没跑完；0.5.2
只调 `Dispose`。

## 0.5.1：清场不能碰共享 baked mesh

0.5.0 用 `VehicleSpawn.Dispose()`（内部 `factory.Destroy`）清场，结果用户反馈：结束一局、回主菜单、
再进一局，玩家坦克履带消失、无法操控。显然 `factory.Destroy` 释放了跨载具共享的 baked mesh
（履带等），下一局组装复用已释放的网格。

0.5.1：

* 清场只 `VehicleRegister.Deregister(vehicle)` + `root.gameObject.SetActive(false)`；
* 增加 `GameController.Release` 前缀，在离场前注销/隐藏，避免它们参与场景拆除；
* 切场景只清列表，不 Dispose。

## 0.5.0：回编辑器清场

载具是 `VehicleSpawner.Spawn` 直接生成的，游戏不会把它们登记进任何 `StageVehicleSpawnEvent`
的 `spawns` 列表，所以回编辑器时也不会被清理。

做法：

* 每 0.25 s 读一次 `Player.CurrentState.StateName`（设计师状态的字符串是 **"Vehicle Editor"**，
  见 `VehicleDesignerPlayerState.get_StateName` 的 ISIL），状态变化时打 `[state]`；
* 进入 Editor 后对本插件生成过的每个 `VehicleSpawn`：先 `VehicleRegister.Deregister(vehicle)`，
  再 `VehicleSpawn.Dispose()`（内部 `factory.Destroy(vehicle)`）；
* `VehicleSpawn` 放静态 `List` 里强引用，过期场景切换时只清列表不 Dispose（物体随场景销毁）；
* 如果生成任务在状态切换后才完成，下一次轮询会再清一次。

## 0.4.2：可用的 IMGUI 只有 Box/Label

0.4.1 日志：`GUILayout.BeginArea(Rect)` → `NotSupportedException: Method unstripping failed`。
在 `dump/dump.cs` 里查 `UnityEngine.GUI`（TypeDefIndex 13691）确认，构建只保留了：

```
GUI.Label(Rect, string)
GUI.Label(Rect, GUIContent, GUIStyle)
GUI.Box(Rect, string)
GUI.Box(Rect, string, GUIStyle)
GUI.Box(Rect, GUIContent, GUIStyle)
```

没有 Button / Window / BeginArea / ScrollView / TextField / DrawTexture。
所以面板只能用 `GUI.Box` + `GUI.Label(Rect, string)` 绝对坐标画；当前项用 `GUI.color` 标黄。
没有鼠标交互，F8/F6/Z/B 仍是唯一控制方式。

## 0.4.1：GUILayout.Window 不可用

0.4.0 日志：

```
[ui] OnGUI failed: System.MissingMethodException:
Method not found: 'Void LayoutedWindow..ctor(WindowFunction, Rect, GUIContent,
Il2CppReferenceArray`1<GUILayoutOption>, GUIStyle)'.
```

`GUILayout.Window` 内部 new 的 `LayoutedWindow` 构造函数在 interop 程序集里签名不匹配，运行期直接炸。
0.4.1 改成 `GUI.Box(rect, title)` + `GUILayout.BeginArea` + `GUILayout.Label`，不碰 Window，
也不做滚动条/按钮；显示当前项前后各 10 条。

另外去掉了每次生成后调用的 `Probe.DumpVehicleRegister()`（它拿 `GameMode` 基类代理反射不到
`sharedState`，只会在日志里刷 “no register field reachable”），`[track]` 保留 10 秒。

## 0.4.0：准星落点与 IMGUI

* 落点：`Player.Cameras.ActiveCamera` → `ScreenPointToRay(屏幕中心)` → `Physics.RaycastAll`
  （`QueryTriggerInteraction.Ignore`）。必须跳过玩家自己的车：通过
  `VehicleController.controlTarget` 反射拿 `IVehicleBehaviour`，`TryCast<IAIControllableVehicle>()`
  取 `transform.root`，再用 `hit.collider.transform.IsChildOf(root)` 过滤。
  interop 接口之间 `is/as` 不可靠，全部用 `TryCast`。
* UI：`ClassInjector.RegisterTypeInIl2Cpp<SpawnMenuUi>()` + `AddComponent`，`OnGUI` 里
  `GUILayout.Window`。注意 interop 的 `GUI.WindowFunction` 是 MulticastDelegate，带
  `op_Implicit(Action<int>)`，所以字段用 `Action<int>` 再隐式转换，不能 `new GUI.WindowFunction(method)`。
* 列表按钮需要鼠标；游戏在战斗中可能锁鼠标，所以键盘 F8/F6 + Z 仍是主路径。

## 0.3.2：`as` 接口转换失败 + 原点不在车底

0.3.1 日志：`spawned vehicle is not IVehicleGateway`。`VehicleSpawn.Vehicle` 的代理静态类型是
`IVehicleEditGateway`，但 interop 生成的接口代理之间 **`as`/`is` 不可靠**，必须
`proxy.TryCast<IVehicleGateway>()`（或 `TryCast<Vehicle>()`）。所以 0.3.1 的物理/追踪都没跑。

另一个问题：蓝图原点不在车底。0.2 m 时车体埋进地形 → “闪一下消失”；2 m 时可见但悬空。
0.3.2 用 MeshRenderer 包围盒把车底对齐到射线地面，再开物理；Rigidbody 取子物体里质量最大的
（轮子/炮塔的 Rigidbody 质量很小）。

## 0.3.1：悬空 = 少了 isKinematic=false

`StageVehicleSpawnEvent.SpawnAsync` 在 `Spawn` 之后会遍历新载具并调
`Rigidbody.set_isKinematic(false)`（ISIL 约 321-324 行）。直接调 `Spawner.Spawn` 不会执行这段，
所以载具保持 kinematic，悬在落点高度不动。

0.3.1：生成完成后 `gateway.transform.GetComponent<Rigidbody>()`（找不到就
`GetComponentInChildren<Rigidbody>(true)`），设 `isKinematic=false`、`useGravity=true`；
`Height` 回到 0.2，靠物理落到地面。0.3.0 的 trigger 过滤保留。

## 0.3.0：生成后消失

0.2.0 落点 y=0.2 时坦克“闪一下消失”。0.3.0 的处理：

* `Physics.Raycast(..., QueryTriggerInteraction.Ignore)`，并打印
  `hit.collider.name / layer / isTrigger`；沙盒里的生成区/水面 trigger 是首要嫌疑；
* `Height` 默认 2 m（相对命中表面），避免出生时和地形碰撞体互相嵌入；
* 生成后保留 `VehicleSpawn` / `IVehicleGateway` 强引用，并每 1 秒打 `[track]`（位置、active、
  `TotalRegisteredCount`），15 秒。用于区分：掉出世界（y 持续下降）、被销毁（访问 transform 抛
  MissingReference）、被注销（registered 下降）。

## 0.2.0：落点与朝向

0.1.4 已经能成功生成（`RanToCompletion`、`BehaviourEnabled=True`、手动 Register 后计数递增）。
用户反馈两个体验问题：落点不在平地、朝向跟玩家视角走。改为：

* `Distance` 默认 150；`GroundSnap` 在生成点 `(x, player.y+300, z)` 向下 `Physics.Raycast`，
  取 `hit.point.y + Height`；
* `FacePlayer` 用 `Quaternion.LookRotation(playerPos - spawnPos)`，只取水平方向；
  `FacingOffsetDegrees` 处理蓝图车头反向的情况；
* 旧 cfg 的 `Distance=40` / `Height=1` 通过 `ConfigVersion` 迁移一次，避免默认值改了不生效。

## 0.1.4：自己的 `== null` 把 Spawn 又搞崩了

0.1.3 日志的栈：

```
NullReferenceException
   at Il2CppInterop.Runtime.IL2CPP.Il2CppObjectBaseToPtrNotNull(Il2CppObjectBase obj)
   at Il2CppSystem.Threading.CancellationToken.op_Equality(CancellationToken left, CancellationToken right)
   at SprocketSpawnMenu.SpawnTest.TrySpawn()
```

`CancellationToken` 的 interop 类型重载了 `op_Equality`，所以 `cancellationToken == null` 不是引用比较，
而是调 native，然后对 null 抛 NRE。换成 `ReferenceEquals(cancellationToken, null)`；
`None` 万一为空时用 `new Il2CppSystem.Threading.CancellationToken(false)`。

> 规则：interop 代理对象判空一律 `ReferenceEquals`，别用 `==`。

## 0.1.3：Spawn 的 NullReferenceException

0.1.2 日志里 Z 已经触发，但 `VehicleSpawner.Spawn` 同步抛 NRE：

```
System.NullReferenceException
   at Il2CppInterop.Runtime.IL2CPP.Il2CppObjectBaseToPtrNotNull(Il2CppObjectBase obj)
   at Sprocket.Vehicles.Spawning.VehicleSpawner.Spawn(IVehicleBlueprint, VehicleSpawnInstance,
        VehicleSpawnOptions, CancellationToken)
```

用 Mono.Cecil 读 interop 程序集确认了签名：

```
Spawn(IVehicleBlueprint, VehicleSpawnInstance, VehicleSpawnOptions,
      Il2CppSystem.Threading.CancellationToken ct)
  ct: Il2CppSystem.Threading.CancellationToken  valueType=False   ← 引用类型
```

所以 `default` 是 null，interop 的 `NotNull` 直接抛。修复：传
`Il2CppSystem.Threading.CancellationToken.None`（interop 里有 `get_None()`）。

同时把生成方向改成**水平前方**：玩家低头时 `transform.forward` 有负 y，40 米外会生成到地下
（0.1.2 日志里第一次 pos.y = -0.96）。

第二个问题：`VehicleSpawner.Spawn` **不负责注册**。游戏里 `StageVehicleSpawnEvent.SpawnAsync`
在 `Spawn` 之后会用 `IVehicleRegister.Register` 把载具登记进去；直接调 `Spawn` 会漏掉这一步，
载具可能生成出来但不参与 `VehicleUpdate/VehicleFixedUpdate`（AI 不动）。0.1.3 因此：

* 通过 `ScenarioGameMode.sharedState.VehicleRegister` / `DeathmatchGameMode.vehicleRegister`
  拿具体 `VehicleRegister`（`TryCast<VehicleRegister>()`，接口代理没有 `TotalRegisteredCount`）；
* 生成完成后比较 `TotalRegisteredCount`，没增加就手动 `Register(vehicle)`。

> 复现签名检查的方法：`inspect` 小工具（Mono.Cecil 0.11.4）读
> `BepInEx/interop/*.dll`，比猜 interop 包装器类型可靠。工具不在插件工程里。

## 0.1.2：F10 收不到

0.1.1 的日志证明 **F8/F6 是生效的**（`[select] selected 24/65 → 23 → 22 → 21`），只是没有界面提示；
但 **F10 完全没有产生任何 `[key]`/`[spawn]` 行**，说明按键没到插件（笔记本常把 F10 当静音键，
Proton 收不到）。0.1.2 加：

* `SpawnFallbackKey`（默认 `Z`），与 `SpawnKey` 二选一触发；
* 每次按键写 `[key] <键> -> <动作>`；
* 启动时打印 `Hotkey.Describe()`，可直接看出 `'F10' -> F10` 还是 `<unparsed>`。

另一个坑：**改配置默认值不会迁移已有 cfg**。0.1.1 把 `AutoProbeOnSceneLoad` 默认改成 false，
但 0.1.0 生成的 cfg 里仍是 true，所以 0.1.1 的日志里自动探针又跑了一次。要真正关掉必须改文件或删 cfg。

## 0.1.1：沙盒卡死问题的定位与修复

用户第一次实测（Fedora + Proton，Wine 11）在**点沙盒“开始”按钮、可以操作坦克时**卡住。
日志（`LogOutput.log`，0.1.0）里没有 `[spawn]`，说明不是生成导致的；探针在
`scene=Sandbox`、`frames=4186 realtime=31.6` 时正常跑完，随后只剩 AI 散布模组的 `[gun]` 日志。

0.1.0 每帧做了两件不该做的事：

1. `Probe.MaybeAutoDump()` 在 `_autoDumped` 检查**之前**就调用 `FindObjectsByType<GameController>()`，
   即**每帧全场景扫描**，自动探针跑完后也不停。沙盒点“开始”会一次性加载玩家设计坦克 + 固定坦克
   （大量 GameObject），扫描成本在这时被放大，表现就是卡死。
2. `Hotkey.WasPressed()` 在 InputSystem 没报告按键时会继续调用 legacy `Input.GetKeyDown()`。
   游戏只启用新 InputSystem 时这会每帧抛异常（被 catch，但每帧 3 次），在 Proton 下加重 GC/主线程负担。

0.1.1：

* `MaybeAutoDump` 先按 1 秒节流 + 场景名判断，扫描每个场景只做一次；`_autoDumped` 后不再扫描。
* 热键只用一个后端，`Key`/`KeyCode` 解析结果缓存；legacy 只在 InputSystem 不可用时尝试，抛一次就永久停用。
* 只挂 `GameController.SceneUpdate`；`GameMode.GameModeUpdate`（三指令尾跳桩）只在 SceneUpdate 挂不上时兜底。
* 探针不再调用 `VehicleSource.GetBlueprint()` / `GetFactories()`，避免提前加载蓝图或创建组装工厂。
* `AutoProbeOnSceneLoad` 默认改为 **false**：0.1.1 先单独验证“点开始是否还卡”，探针改为手动 F9。
* 每 10 秒 `[tick] alive frame=... fps=...`，用于判断卡住时主线程是否还在跑。

## 0.1.0 探针在沙盒里拿到的结果（已确认）

* `scene=Sandbox`，`GameController state=Running`，GameMode 的 `Mode = Sandbox | Mission`（flags=3）。
* 场景里**有** `VehicleSpawner` ×2：`150m Spawner` 和 `250m Spawner`，都是 `Team1 / Group1`。
* `VehicleSource` ×2：
  * `150m Spawner`：`Mode=EditorExitSave`，`BlueprintName=SandboxTarget150m`，`Source=StreamingAssets`；
  * `250m Spawner`：`Mode=Explicit`，`BlueprintName=SandboxTarget300m`，`Source=StreamingAssets`。
